# 需求文档回正：从"模块优先"改成五步主流程

**日期**：2026-09-17
**状态**：已实现
**相关文件**：`docs/rebuild/PRODUCT_REQUIREMENTS.md`、`FUNCTIONAL_REQUIREMENTS.md`、`REBUILD_PLAN.md`、`NON_GOALS.md`（新建）、`README.md`、`REQUIREMENT_TRACEABILITY.md`

## 背景：一次全项目扫描的发现

用户说"感觉积重难返，怎么改都改不动，还越变越糟"，要求扫描整个项目。扫描（只读，未改代码）查出四件事，其中第一件是决定性的。

### 一、主流程在界面上没有入口

```ts
// App.tsx:75
const auxiliary = !geometryLevel && (conceptPane === "inputs" || conceptPane === "recognition");
// store:392
setConceptPane: (conceptPane) => set({ conceptPane }),
```

`setConceptPane` **在整个仓库里没有任何调用者**。`"inputs"` / `"recognition"` 只出现在类型定义和 `App.tsx` 的读取处。于是：

- `ConceptInputsBoard`（上传逻辑拓扑图）—— 打不开
- `ConceptRecognitionBoard`（候选识别、图上标节点）—— 打不开

两个面板写在代码里、`import` 在 `App` 里、逻辑完整，**没有任何按钮能走到**。

更进一层：代码里的"识别"不是自动的，是个五步人工外挂回路（上传 → 同步给本地服务 → 在 DSH 里叫 agent 读图 → 拉取候选 → 逐条勾选采用）。`diagram-import.ts` 吃的是别人解析好的 JSON，`concept-candidate.ts` 全是"人工排除"的交互——**没有任何一行把图片像素变成拓扑节点**。

对照用户定义的目标第一条"上传逻辑拓扑图 → 自动拆成逻辑节点"：第 2 步没有程序实现，第 1 步连入口都没接上。

### 二、"改不动"是结构性的，不是手艺问题

3D 预览与 UE 导出都从 `resolveAssembly()` 出发，而它解析的是 `modules + instances + connections`：

- `PreviewPanel.tsx:59-61` — `resolveAssembly(snapshot)` → `buildDeploymentGeometry(snapshot, instances)`
- `ue-plan.ts:41-50` — `for (const instance of resolution.instances)` → `actorSyncKey(projectId, instance.id, block.id, scopePath)`

而 `LogicNode` 只有一个 `moduleId` 指针，**不能直接持有几何**。

所以删模块层 = 3D 白屏 + UE 导出归零。前两次重构整轮回退，根因不是"没确认预算"这个现象，而是**先删承重墙，再想房子怎么盖**。

### 三、需求文档在唱反调

`AGENTS.md` 要求"改产品行为必须先改 `docs/rebuild/`"，而三份权威文档还停在模块优先模型上（`PRODUCT_REQUIREMENTS.md` 仍写 `Draft 1`）。原 15 条 FR 里约 10 条是模块架构长出来的枝。每次开工按约定读需求，就等于每次被加一遍活儿，而这些活儿正指向要拆掉的那层。

**这是"越改越糟"的直接来源**：不是需求太多，是权威文本和真实目标方向相反。

### 四、其余量到的问题

- 三套坐标、指纹链、诚实规则、设计日志机制是**真资产**；类型 0 错误、184 测试全过、运行期 0 控制台错误。
- `DecompositionCanvas` 把"模块框"当画布节点画（`nodeTypes = { logic, moduleFrame }`），和真节点抢拖拽/选择/折叠/连线——削模块最麻烦的地方就在这。
- 参考图以 base64 存在项目 JSON 里，每次编辑防抖 350ms 序列化整份项目进 localStorage。
- `scripts/export-ue-actors.mjs` 与 `ue-plan.ts` 各有一套连接求解，靠注释约定一致，没有测试锁住。

## 决定

**目标定义收敛为五步**：

```
上传逻辑拓扑图 → 节点 → 节点里拼模型 → 3D 预览 → 导出 UE
```

删掉流程里"模块"这一步。节点是唯一容器：内部要么是几何（叶子），要么是逻辑拓扑（复合）。

**范围冻结写进四份文档**：`PRODUCT_REQUIREMENTS.md` 重写为 Draft 2，`FUNCTIONAL_REQUIREMENTS.md` 从 15 条收敛到 8 条 P0（含旧 FR 处置对照表），`REBUILD_PLAN.md` 的阶段按节点模型重排，**新建 `NON_GOALS.md`** 把"明确不做"从各文档的尾巴里抽出来单独成文。

**交付顺序反过来：先让主流程在节点上跑通，再删模块层。**

```
1-B  LogicNode 加 blocks + childScopeId
1-C  3D 预览 + UE 导出改吃展平节点几何   ← 先切这一刀
1-D  识别入口接上
1-E  节点嵌套导航打磨
1-F  模块层才删
```

原 S2-5（UE 导出改吃节点几何）排在最后，因为它在"清理"逻辑里；提到 1-C，因为**它才是解除锁死的那个动作**。

## 考虑过的选项

### `NON_GOALS.md` 单独成文，还是继续散在各文档末尾？

| 选项 | 代价 |
|---|---|
| **单独成文 + 写明每条的重新评估条件** ✅ | 多一个文件；要求每次改范围动两处 |
| 继续散在 `PRODUCT_REQUIREMENTS.md` §6 和 `REBUILD_PLAN.md` §7 | "不做"散落各处，读需求的人只看要做的那份，不做的那份永远读不到 |

选前者。理由是这次扫描暴露的病就是"权威文本互相矛盾"，而"不做"清单是最容易被忽略、又最能防止范围反弹的一份。

### 识图用哪条路？

| 选项 | 代价 |
|---|---|
| 工具内接按钮 + 本地 agent 读图 ✅（用户选定） | 每次识别需要 agent 在场 |
| 工具自己接多模态 API | 接供应商、管 Key、超时重试，工程量大一个量级 |
| 先不做识别，手工画节点 | 产品定义第 1 条成功标准悬空 |

用户选了第一条，并且**当前先不做识别**，优先做文档回正。

### 过时文档：改写还是加标注？

| 选项 | 代价 |
|---|---|
| **加取代横幅 + 在索引里标"待改写"** ✅ | 短期内新旧并存，需要读横幅 |
| 立刻逐份重写 | `TWO_STAGE_ARCHITECTURE.md` 476 行，改写本身是一次大工程，会和范围冻结混在一个回合里 |

选前者。理由是纪律第 3 条：**不要在一个回合里既改功能又换模型**——这次只换定义，改写留给独立一步。

## 放弃或推迟了什么

- **放弃"两个工作面"**（09-16 的决定再次被修正）。顶层页签本身就是要修的病。
- **放弃模块作为复用单位**。复用改由节点嵌套承担；跨节点复用同一子树列为 P1，且明确是**树**不是图。
- **放弃模块分文件保存、Git 三方合并、UE Apply/回读**（移入 NON_GOALS）。
- **推迟**：过时文档的逐份改写；识图入口的接线（用户选择先只改文档）。
