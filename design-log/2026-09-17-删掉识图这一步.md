# 删掉识图这一步：主流程从五步变四步

**日期**：2026-09-17（同日晚，接在"删掉模块层"之后）
**状态**：已实现
**相关文件**：`docs/rebuild/PRODUCT_REQUIREMENTS.md` §3.1、`FUNCTIONAL_REQUIREMENTS.md` FR-02、`NON_GOALS.md` 二·补；代码侧删了 `concept-candidate`、两个识别面板、`server/concept-bridge.ts`、`data/concept/`

---

## 决定

**把"上传逻辑拓扑图 → 识别出节点"从产品里删掉。** 不是推迟，不是换路线 —— 是不做。

主流程因此从五步变四步：

```
① 画布上摆区域、连路线（手工建节点）
② 节点内部拼模型
③ 3D 预览
④ 导出到 UE
```

## 为什么

用户给的理由是"**这一步需要灵活定位，所以不要了**"。这句话值得展开，因为它是整件事的关键：

**识图要成立，工具得先猜三样东西** —— 图上的方位、图与厘米的比例、哪条线算连通。
这三样都不是能从像素里可靠读出来的：同一张手绘图，正着看和歪着看是两个结果；
作者画的框子大小不代表真实尺寸；两条线相交也不一定表示连通。

于是无论识别得多准，**人还是得把每一条都核对一遍**。核对的时间加上去，
这条路线就比"直接画"更慢 —— 而手绘拓扑图上的区域通常只有十几个，
摆位置、连路线本来就是这工具的主场操作，不是需要绕开的负担。

试过的那条具体路线更放大了这个问题：**上传 → 手动同步给本地服务 → 在别处让 agent 读图 →
拉回来核对**。一次操作拆成四步，其中两步要人离开工具。它整套是走通过的（见下），但走通之后
结论是"绕得超过它省下的手工"。

## 考虑过的选项

| 选项 | 代价 |
|---|---|
| **整条删掉** ✅ | 主流程少一步，工具少一个必须维护的入口。代价是**放弃一条已经写好的成功标准** |
| 保留代码，只是不从界面进 | 就是"面板存在但走不到"那个病，而且是我们刚花力气修掉的那个 |
| 换一条新路线（工具内接多模态 API） | 要接供应商、管 Key、处理超时重试；准确率仍要人工复核。**猜方位比例这个根本问题不解决**，换谁来读图都一样 |

选第一个。第三条被否的理由是它**没有解决真正的问题**：问题不在"谁来看图"，
在"看了图也定不出方位与比例"。

## 放弃了什么（要写清楚）

- **产品原第 1 条成功标准**："一张手绘逻辑拓扑图进去，一张可编辑的逻辑拓扑出来"。
  现在的第 1 条是"手工摆出区域与路线"。**这是主动降低一条成功标准，不是把它做得更好了。**
- **一整套已经走通的代码**：候选模型与校验、图上叠加、逐条勾选、拖动修正、
  按输入指纹拒绝沿用旧结论、`/api/concept/*` 三个端点、输入材料落盘给 agent 读图的机制。
  实测走通过一整圈（上传 1265×805 的图 → 落盘为合法 PNG → 推候选 → 拉取 → 排除一条 →
  采用 → 节点带角色与标高进画布）。**这套东西是有价值的，只是价值不在这个产品里。**
- **`data/concept/`**：样例候选与输入暂存目录。

## 没有一起删的

指纹（digest）机制、同名资料不猜版本、"输入变了就拒绝沿用旧结论" ——
这些是通用做法，与识图无关，仍在别处使用。**不要因为"它们是为识图写的"就一起清掉。**

「参考资料」这一格留下了（原「输入上下文」）：它现在是"放着看的图与文字"，
工具不解析它们。改的只是措辞 —— 原来的文案还在说"识别会被拒绝""先同步给本地服务"，
指向一个不存在的东西了。

## 已知边界与风险

- **`LogicInputKind` 里的 `logic-topology` / `scope-map` 两个键名保留了。** 它们的**标签**已经改成
  面向人的参考材料说法，但键名还是旧的 —— 改名意味着给已有草稿做数据迁移，收益不值。
  这是一处"名字与含义不完全一致"，记在这里免得下次有人以为是 bug。
- **`LogicInputCalibration`（比例标定）还在。** 它的用途是"图上的像素 ↔ 厘米"，
  原本服务于识图。现在它只对"你自己看图量距离"有意义。没用上，但删了要动 schema，先留着。
- **`DecompositionProposal`（登记一次结果 + 指纹）还在。** 识别候选是它最大的使用者，
  现在只剩"手工登记"这个用途了。留着，因为它承载的是"下游产物必须携带依据的指纹"这条原则。
- 主流程 ① 现在是**纯手工**，这是已知的能力降级，不是待办。
