## 背景

工具当时能画白盒、能导出 UE，但**"设计"这件事没有位置**。用户的原话是：

> 分两层工具来做。第一步把构想做成"做好的图"，第二步把"做好的图"转化到 UE。与上一步约定格式，让两层能上下咬合。

关键约束：两层之间的约定要是**数据**，不能是"照着上一步的截图再做一遍"。

## 坐标与指纹不是一回事

这是整轮最容易搞混、也最容易写出 bug 的地方。最后定成三套坐标，**互不换算**：

| | 含义 | 谁产生 | 用途 |
|---|---|---|---|
| `graphPosition` | 画布排版 | 拖拽 | **只影响看，不影响几何** |
| 模块局部厘米 | 模块内部相对位置 | 阶段一拆解（依范围图） | 体块与端口 |
| 世界坐标 | 关卡里的真实位置 | 只在整体组装时产生 | 3D / UE |

**放弃的做法**：让画布坐标兼职几何坐标。曾经这么干过，后果是"排版动一下，草案就过期"，以及把厘米当画布坐标用导致画布被挤成看不见的小点。移动排版现在**不修改几何、不使草案过期**。

一致性靠**指纹**（FNV-1a，同步、浏览器和 Node 都能算）：

```
输入包 digest ──> 识别候选必须携带它，否则拒绝
拓扑 digest  ──┐
划分 digest  ──┴─> 拆解/构型提案必须携带，漂移就拒绝采用
```

下游产物一律**带着它依据的指纹**，上游一动就作废。宁可让人重新生成，也不静默沿用旧结论。

## 组装求解器会和你打架

阶段一给出的相对位置，和阶段二求解器的约束，是两套说法：

- 概念说：这两个区域相距 10 米
- 求解器说：有连接的模块必须端口对端口，楼梯还得前移 400、抬升 300

**踩过的坑**：按概念摆好实例再连线，求解器会把模块全部挪走。

**解法**：连线时把概念里的实际间距量出来写进 `connection.spacing`。这样求解器的解与概念摆放**逐一致**。实测结果是 3D 预览报"端口约束闭合、0 项规范提示"。

## 端口定位：支撑函数不是交点

`portPose` 一开始用矩形**支撑函数** `|ux|·w/2 + |uy|·d/2`。那是"投影范围"，不是"射线与边界的交点距离"——**斜方向时端口会甩到体块外面**。轴向时两个公式恰好相等，所以测试没抓到，是看渲染才发现的。

正确做法是两轴射线距离取小值：`min((w/2)/|ux|, (d/2)/|uy|)`。

**教训**：几何公式在特例上对，不代表对。补了 45° 斜向的回归测试。

## 递归嵌套：作用域可复用，所以必须有环检测

用户要求"层层嵌套，深度不限"（游乐园 → 鬼屋 → 小鬼屋），并且确认**作用域可以作为可复用资产**（同一个鬼屋用在两张地图里）。

- 作用域放在**扁平池**里，模块通过 `childScopeId` 引用。
- 可复用 ⇒ 可能自包含 ⇒ **必须有环检测**，外加递归深度护栏。
- 管线（链路、拆解、构型）本来就是**按作用域独立**的，所以没有重写，而是加了 `scopeViews()` 让既有逻辑每层各跑一遍再合并。

**放弃的做法**：内联嵌套（简单、不可能成环，但无法复用）。复用是用户明确确认的需求，不能因为实现方便就丢掉。

### 共享作用域会撞车（设计预言成真）

设计文档里写过一句警告："嵌套后三段 ID 不再唯一，会导致两个鬼屋里的同名积木撞车"。

实现时**真的撞了**：我按 `moduleId` 记实例，同一个作用域被两条路径引用时，第二条把第一条覆盖了。

改成按 **(路径 + 模块)** 记实例，连接逐分支生成。同步键也随之升级：

```
旧：projectId / instanceId / blockId
新：projectId / 作用域路径… / instanceId / blockId
```

**诚实说明**：`instanceId` 是 UUID，本来就不会撞。路径段的真正价值是重新生成时身份稳定、能从键直接看出"这块积木属于哪栋楼的哪一层"。

## 已知边界与风险

- **指向已展开模块的链路接不上**：它在阶段二里是一组实例，没有单一实例可接。现在会被 `skippedLinks` 明确报出来，而不是悄悄丢掉。要真正接上需要约定"从子层的哪个入口进"——这是设计问题，不是 bug。
- 平面位置图读的是**已落成**的模块定义，不是待确认候选；套用后候选清空也不会变成虚线。
- 嵌套实测只压到两层，三层以上未验证。
