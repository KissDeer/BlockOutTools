# 设计日志目录

记录 BlockOutTools 的**设计过程与思路**：想过什么、比较过什么、为什么这么定、后来推翻了什么。

## 和 `docs/rebuild/` 的分工

| | `design-log/`（这里） | `docs/rebuild/` |
|---|---|---|
| 记什么 | 过程与理由 | 需求与契约 |
| 语气 | 可以犹豫、可以自我更正 | 确定、经确认 |
| 生命周期 | 按时间累积，废弃的保留 | 被取代就改写 |
| 改了会怎样 | 只影响理解 | 改产品行为必须先改这里 |

**冲突时以 `docs/rebuild/` 为准。** 这里解释"为什么"，不定义"必须是什么"。

## 怎么用

**开始做事前**：读 `INDEX.md`，按索引找相关条目，再读对应文件。已经踩过的坑不要再踩一遍。

**结束对话前**（`AGENTS.md` 里的硬性要求）：

1. 新开 `YYYY-MM-DD-主题.md`，同一天多个主题就多开文件。
2. 在 `INDEX.md` 加一行。
3. 只记决策与理由——**不抄代码、不贴 diff**。

## 一个条目该写什么

```markdown
# 标题

日期 / 状态 / 相关提交 / 相关文档

## 背景
为什么现在要处理这件事。

## 考虑过的选项
列出来，写清各自的代价。只写最后选的那个等于没记录。

## 决定
选了什么，为什么。

## 放弃或推迟了什么
明确写出来。这是最有价值的部分。

## 已知边界与风险
现在还没解决的、可能是错的、需要将来验证的。

## 后来怎样了
（后续对话补写）如果这个决定被推翻或修正，在这里写明。
```

## 约定

- 状态用 `提案` / `已实现` / `部分实现` / `已废弃`。
- **废弃的条目不删除**，标注被什么取代。设计的价值一半在于知道哪些路走不通。
- 发现旧结论错了，就地更正并写明原因——不要悄悄改掉痕迹。
- 当天没结论也可以记，标 `提案`。
