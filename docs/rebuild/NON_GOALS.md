# 明确不做

状态：`Draft 1 · 2026-09-17`
性质：**本文是 [PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md) 的组成部分，不是附录。**

---

## 这份文件怎么用

**任何条目想回到范围内，必须先改这里，并写明"重新评估的条件"，再动代码。**

不这么做的后果有实测证据：本项目长期同时维护 15 条功能需求，其中约 10 条是"模块优先"架构延伸出来的。每次开工按约定读需求，就等于每次被加一遍活儿，而这些活儿正指向要拆掉的那一层。这不是需求太多，是**权威文档在唱反调**。

## 三条硬规矩

1. **不为了"以后可能有用"留一层。** 多一层包装的代价是确定的，收益是想象的。
2. **不因为旧代码已经写了就保留。** 沉没成本不是需求。删掉写好的代码比长期背着它便宜。
3. **不把"能演示"当"已实现"。** 面板存在、API 存在、测试通过，都不等于用户在界面上走得到。

## 一、整块删除（Draft 1 的核心，现已废弃）

| 不做的事 | 为什么 | 重新评估条件 |
|---|---|---|
| **模块定义 / 模块实例 / 多实例复用** | 用户原话："没意义的事情就不做了，模块不需要了。" 几何直接挂节点；复用改由嵌套承担，粒度更自然 | 出现真实需求：同一个子树要在多处复用且改动要同步。届时按**节点子树引用**设计，不复活"模块"这个词 |
| **一个子作用域被多个节点共用** | 嵌套是一棵树，不是图。`childScopeId` 移到节点上时就从多对一收紧成一对一（2026-09-17 之前代码支持多对一，属于主动放弃） | 与上一条同时评估：出现真实的子树复用需求时，按引用设计并放开 |
| **拆解页 / 构型页** | 分组不产生新信息；构型就是节点自己的几何 | 不评估 |
| **"放入整体"这个动作** | 节点本来就在地图里，不存在"放" | 不评估 |
| **顶层页签（任何两个）** | 切过去以后不知道从属于哪个逻辑节点，也没办法整体观察。这个毛病和模块无关，换任何两个页签都有 | 不评估。层级只能用画布焦点 + 面包屑 + 层级树表达 |

## 二、当前不做（方向可能成立，但现在不做）

每条都写明**重新评估的条件**——这是"不做"和"否决"的区别。

| 不做的事 | 为什么现在不做 | 重新评估条件 |
|---|---|---|
| **区域 / 链路级资料附件** | 项目级 + 节点级两级够用 | 出现"某个区域有专属要求"的真实用例 |
| **Git 三方合并与逐字段冲突 UI** | 单人本地创作，没有并发编辑 | 真的出现两人改同一项目 |
| **项目分文件保存** | 单文件 + 本机草稿够用。分文件的收益是协作与合并，那两件事都不做 | 项目文件大到打开变慢，或开始用 Git 管理 |
| **UE Apply / 回读 / 连接 Editor** | 导出 Actor 计划交给人执行已经闭环。真实 UE 写入要处理幂等、失败清理、地图不自动保存，是一整套 | 手工导入开始出错或太频繁 |
| **AI 通用命令协议**（任意对象 patch） | 当前没有自动模型调用，AI 用途只有"局部草案"一种 | 出现第二种需要 AI 批量改的场景 |
| **白盒规范的可配置参数全集**（胶囊、跨步、跳跃、落脚区、坡道…） | 先跑通主流程。规范本身不是瓶颈 | 主流程稳定，且规范检查真的抓到问题 |
| **3D 预览与 2D 双向选择联动** | 单向（2D → 3D 高亮）够用 | 不评估 |
| **连接器自动几何求解** | 连接表达拓扑和语义即可；自动生成楼梯/坡道几何是独立一大块 | 不评估 |
| **性能目标（具体数字）** | 还不知道真实项目的量级 | 实测开始卡 |
| **多格式 3D 导出**（FBX / GLTF / OBJ） | UE 是唯一三维落地目标 | 出现第二个落地目标 |
| **手机端 / 触屏** | 桌面键鼠工具 | 不评估 |
| **截图 / PNG / SVG 导出、只读分享包** | 审阅用途，不影响生产闭环 | 不评估 |

## 二·补、识图：整条不做（2026-09-17 决定）

**从产品里删除，不是推迟。** 原定义的第 1 步是"上传逻辑拓扑图 → 识别出节点"，
现在没有这一步了，主流程从五步变成四步。完整理由见
[PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md) §3.1，这里只留结论与后果：

| 试过的路线 | 为什么放弃 |
|---|---|
| **上传 → 手动同步给本地服务 → 在别处让 agent 读图 → 拉回来核对** | 用户判断：太绕。一次操作拆四步，两步要人离开工具，还要 agent 全程在场 —— 绕得超过它省下的手工。**代码曾整套走通，已全部删除** |
| **工具内全自动识图**（内置 CV / 接多模态 API） | 同样不做：要接供应商、管 Key、处理超时重试，准确率仍要人工复核 |

**根本原因写在这里，因为它比"路线选错了"更值得记**：

> 这一步要求工具去**猜"灵活定位"** —— 图上的方位、比例、哪条线算连通，都是要靠人盯出来的。
> 猜出来的位置比让人直接画还慢，因为人得先核对一遍才敢用。

**放弃的代价**：产品原第 1 条成功标准——"一张手绘逻辑拓扑图进去，一张可编辑的逻辑拓扑图出来"——
不再成立。现在是"手工摆出区域与路线"。这是**主动降低一条成功标准**。

**重新评估条件**：不再评估。若以后真要做，它会是一个**独立的新功能**（且必须自己想清楚
方位与比例从哪来），不是把这条老路线捡回来。

**没有一起删掉的**：拓扑/上下文/几何的指纹（digest）、同名资料不猜版本、
"输入变了就拒绝沿用旧结论"这类通用做法 —— 它们与识图无关，仍在别处使用。

## 三、永久否决（不再讨论）

- 一比一复刻外部 LayoutTools
- 把 3D 预览做成独立建模器
- 让 AI 操作 DOM、模拟鼠标、绕过参数 Schema
- 用名称或几何匹配作为 UE Actor 的日常同步兜底（只允许旧数据迁移时显式确认）
- 一个概念有两个出口（两份区域清单、两套拓扑快照、两个"当前模块"）——**这类重复不会自己消失，只会让人不确定该信哪一个**
- 把"能演示"当"已实现"：面板写在代码里但没有入口，不算做了
