**识别采用「agent 读图 + 人工确认」而不是内置 CV**：`同步输入给本地服务`把图片写到 `data/concept/inputs/`，DSH 里的 agent 直接看图后把候选 POST 回来，网页负责核对、修位、逐条取舍与套用。识别只产出候选，不产出结论。

**拆解同样采用「AI 提案 + 规则校准 + 人工确认」**：`同步拓扑给本地服务`把拓扑快照（节点/链路/钥匙/相对位置/楼层 + 两个 digest）交给 agent，agent 给出模块划分提案；网页展示提案，**规则兜底检查**未分配、重复分配、跨层、孤岛、模块图不连通、拆得过碎/过粗；两者都通过才允许套用。模块间连接由拓扑链路推导，不另存一份，避免划分与连接对不上。

**交付门**：`error` 级问题为 0 才允许交付；实测中规则确实抓到了"两段互不相连的区域导致模块图不连通"这一真实数据问题，而不是静默放行。

**S2-A 的硬约定已落地并实测**：连接落成时**必须把概念里的实际间距写成 `connection.spacing`**。否则组装求解器会按类型默认值（比如楼梯固定前移 400、抬升 300）把模块挪走，和概念给的相对位置打架。实测结果是 3D 预览报"端口约束闭合、0 项规范提示"，求解器解出来的位置与概念摆放逐一致。

**跨概念步的可靠性**：构型在积木上写 `provenance`（源 = 拆解模块 id，特征 = 逻辑区域 id / 拓扑链路 id），组装据此把链路接到端口上，**不靠名字匹配**。实测中发现：加 provenance 之前生成的模块定义无法连线——这类"生成物缺出处"的问题会以"缺少端口"的形式暴露出来，而不是悄悄连错。

**S1-B 的硬约定已落地并实测**：必需输入缺失时「登记拆解结果」按钮禁用；登记后补充任何输入，登记结果立刻显示为过期（登记 rev 与当前 rev 并列展示），不会被静默沿用。

**S1-C 的硬约定已落地并实测**：候选带 `basedOnInputsDigest`，与当前输入不一致时套用被拦下并提示重新识别；范围图未标定时只给警告（节点标记为"尚未定位"），不假装有位置。

**顺带完成的既有缺陷修复**：
- `ModuleEditor` / `BlockInspector` 原先只能通过实例解析当前模块，导致"从拓扑节点进入模块"打不开；已改为优先按 `activeModuleId` 解析。
- 输入完整性警告原先用文案当 React key，同名文件的同类问题会撞 key；已改为结构化警告（`{ id, message }`）。
- 套用候选时曾把"相对位置（厘米）"直接当画布坐标用，两套坐标系混用会把画布上的已有节点挤成看不见的小点；已改为按范围图像素等比映射，相对位置单独存放。
- 套用候选时曾用图纸上的标注覆盖链路标签，造成同一张图上出现两条 A；已改为保留唯一标签、把图上标注记进备注。
- 端口定位原先用矩形**支撑函数**（`|ux|·w/2 + |uy|·d/2`），那是投影范围而不是射线与边界的交点距离，斜方向时端口会甩到体块外面；已改为两轴射线距离取小值，并补了斜方向的回归测试。
- 拆解面板与构型面板各自维护一份"交给 agent 的拓扑快照"，构型那份漏了 `links`，导致 agent 看不到连接、生不出端口；已抽成共用的 `features/concept/concept-snapshot.ts`。
- 平面位置图原先读"待确认的候选"，套用后候选被清空就只剩虚线点；已改为读**已落成**的模块定义，并让模块记录自己的 `relativeOrigin`（这也是阶段二拼装必需的数据）。

### 递归嵌套与路径身份（S2-B，已实现）

`LogicTopology` 现在就是**根作用域**，子作用域放在扁平的 `scopes` 池里；模块通过 `childScopeId` 展开成一层。池是扁平的、可被多个模块引用，所以**同一个"鬼屋"能用在两张地图里**（§1.6 的复用要求）。

| 能力 | 位置 | 说明 |
|---|---|---|
| 作用域模型 | `concept.ts` | `LogicScope` 与根同构；`LogicModule.childScopeId`；`collectScopeIssues` 做**自包含（环）检测** |
| 展开 / 收起 / 复用 | `concept-scopes.ts` | 展开会解除模块自己的构型（几何交给子层）；收起只解除引用，作用域留在池子里 |
| 路径推导与展平 | `concept-scopes.ts` | `flattenModules` 递归展平并**累积父级原点**；`scopeCrumbs` 给面包屑 |
| 按作用域跑管线 | `scopeViews()` | 链路、拆解、构型都是按作用域独立的，既有逻辑在每个作用域上各跑一遍再合并 |
| 路径身份 | `ids.ts` / `ue-plan.ts` | 同步键 `projectId / 作用域路径… / instanceId / blockId`；标签同样带层级 |
| 作用域导航 | `ConceptSidebar` / `ConceptDecompositionInspector` | 面包屑 + 「进入 / 展开 / 收起」 |

**实测中抓到的问题（都已修）**：

1. **共享作用域的实例撞车** —— 这是设计里预言的那个坑，真实发生了：同一个作用域被两条路径引用时，我按 `moduleId` 记实例，第二条路径把第一条覆盖了。改为按 **(路径 + 模块)** 记实例，连接也逐分支生成；回归测试断言两条分支各得一个实例、同步键不重复。
2. **离开子作用域后回不去** —— 面包屑只显示"到当前作用域"的路径，根层没有通往子层的入口。补了模块行上的「进入」按钮。
3. **旧草稿被静默丢弃** —— 给根作用域加了 `id`/`name` 两个必填字段，旧草稿解析失败 → 回退到空项目。这正是项目规范里"不允许静默改变旧文件含义"的那条；已加默认值并补了回归测试（旧草稿必须原样解析出来）。
4. **组装按钮在根层被禁用** —— 判断只看当前作用域的模块，而构型在子层。改为覆盖全树。

**已知边界**：指向**已展开**模块的链路无法落成单一连接（它在阶段二里是一组实例），会被 `skippedLinks` 明确报出来，而不是悄悄丢掉。要真正接上，需要约定"从子层的哪个入口进"，这属于下一步。

## 1. 核心结构：递归作用域 Scope

### 1.1 递归的例子

> 一张巨大的地图里放一个**游乐园**，往外连接**小村、山庄**。
> 游乐园本身很大，内部有**马戏团、聚集处、排队处、鬼屋** —— 游乐园自己也需要拓扑图，用模块组成。
> 鬼屋本身可能也需要**拓扑图、氛围图**和自己的模块。

### 1.2 抽象：Scope

```jsonc
Scope = {
  id, name, parentScopeId,
  inputs,                      // ★ 本层的输入上下文包（见 §2.1）
  atmosphere,                  // 本层氛围与风格（可继承、可覆盖）
  topology: { nodes, links, keys, progression },   // 本层逻辑拓扑（无真实位置）
  content: {
    blocks:    [ ... ],                            // 本层自己的体块（可为空）
    instances: [ { childScopeId, transform } ],    // ★ 子 Scope 实例（递归点）
    ports:     [ ... ]                             // 边界端口
  }
}
```

**拓扑节点有两种命运**，这就是"拆解颗粒度"的全部含义：

| 节点类型 | 含义 | 产出 |
| --- | --- | --- |
| **叶子节点** | 一个空间，到底了 | **基础构型**：体块 + 端口 |
| **复合节点** | 内部还要再分 | **展开为子 Scope**，递归下去 |

拆解 = 两个动作：**横向**（哪些节点合并成同一模块）+ **纵向**（哪些节点展开成子 Scope）。

### 1.3 三层坐标语义（重要澄清）

嵌套 + "相对位置" 需要一个清楚的坐标分层，否则会自相矛盾：

| 层 | 含义 | 谁产生 | 参与几何计算？ |
| --- | --- | --- | --- |
| `graphLayout` | 逻辑图的**画布排版** | 用户/自动布局 | ❌ 纯展示 |
| **Scope 局部坐标**（相对，厘米） | 子节点在**父 Scope 内部**的相对位置与高度 | **阶段一拆解**（依范围图） | ✅ 参与本层体块与端口 |
| **世界坐标** | 真实世界位置 | **阶段二组装** | ✅ 最终 3D / UE |

所以"逻辑图与真实位置无关"和"给出相对位置"并不冲突：
**逻辑图不含位置；拆解产出的是父级局部坐标系里的相对位置；世界位置只在阶段二产生。**

### 1.4 精度逐层

精度**每层各自承诺**，越往里越细，但每层纪律一致：

```
顶层地图    ── 体块级：游乐园、小村、山庄的轮廓与相互连接
  └ 游乐园  ── 体块级：马戏团、聚集处、排队处、鬼屋的位置与连接
      └ 鬼屋 ── 体块级：门厅、走廊、展厅……（到底，成为基础构型）
```

### 1.5 氛围继承

- **默认继承**父级；**可按需覆盖**（鬼屋有自己的阴森氛围，覆盖游乐园基调）。
- 有效氛围 = 祖先链叠加 + 本层覆盖。

### 1.6 Scope 是可复用资产（已确认）

同一个"鬼屋"可以用在两张地图里 —— 做法与现有"模块定义 / 模块实例"完全一致：
**Scope 是定义，Scope 实例是摆放**。定义改动确定性地反映到所有实例。

### 1.7 不支持跨层直连（已确认）

跨层连接（深层节点直连顶层）**不做**。理由：外层的大结构已经说定，内部不需要再重复表达连接内容，否则与外层语义重复。

落地约束：**跨层连接必须通过复合节点的边界端口逐层落地**。这同时让身份与校验保持可控。

### 1.8 映射到已有机制（为什么好做）

| 递归 Scope | 现有 app-v2 | 需要的改动 |
| --- | --- | --- |
| Scope 定义 | `ModuleDefinition`（blocks + ports） | 增加 `instances` → **复合模块** |
| 子 Scope 实例 | `ModuleInstance`（transform） | 直接复用 |
| 递归展开 | `assembly-resolver` / `deployment-geometry` | 改为**递归展开** |
| 叶子体块 | `blocks` + `block-library` | 不变 |
| 逻辑链路 | `connections[].type` | 补 `locked-door` / `shortcut` |
| 层级组织 | 无 | 新增（面包屑 + 下钻） |

**递归不需要新引擎**：现有"模块定义 → 实例 → 规范化部署几何"本来就是为组合设计的，改成递归是加一层调用。而且 **UE 是平的**，递归只服务于设计表达，导出时展平。

### 1.9 两道护栏

1. **禁止自包含**：环检测，直接报 `error`。
2. **身份带路径**：`projectId / scopePath… / moduleInstanceId / blockId`。
   嵌套后三段 ID 不再唯一，**不升级会导致两个鬼屋里的同名积木撞车、重复 Apply 产生重叠 Actor**。

## 2. 阶段一 · 构想工作台

### 2.1 输入上下文包（Inputs Bundle）★ 本版核心

你说"拆解时**要把之前的信息看全**"——这必须是一个**强制的数据约定**，而不是靠记性。

```jsonc
{
  "spec": "blockout.concept.inputs",
  "specVersion": 1,
  "scopeId": "sc_amusement-park",
  "revision": 3,                       // 每次增补/修改递增
  "items": [
    { "id": "in_topo_01",  "kind": "logic-topology", "ref": "inputs/topo-01.png",
      "sha256": "…", "addedAt": "…", "note": "手绘逻辑图" },
    { "id": "in_ext_01",   "kind": "scope-map",      "ref": "inputs/extent-01.png",
      "sha256": "…", "calibration": { "cmPerPixel": 2.5, "origin": [0,0], "rotation": 0, "confirmed": true } },
    { "id": "in_mood_01",  "kind": "mood",           "ref": "inputs/mood-01.png", "note": "氛围参考" },
    { "id": "in_rules_01", "kind": "rules",          "ref": "docs/rules-v3.md",   "note": "拆分规范" },
    { "id": "in_note_01",  "kind": "note",           "text": "鬼屋要独立成模块" }
  ],
  "digest": "sha256(全部 item 的 id+sha256 排序拼接)"   // 完整性指纹
}
```

**硬约定（这就是你要的"约定"）：**

1. **任何拆解提案必须携带它依据的 `inputsDigest`。** 没记 digest 的提案视为不合法。
2. **提案前必须读取并核对全部 items**（拓扑图、范围图、规则、说明）。**缺项必须显式报告**，不允许"凭印象拆"。
3. **输入可后续补充**：新增/修改 → `revision` 递增 → 已有提案标记 `stale`（可对比、可重跑），**不静默沿用**。

### 2.2 四类输入

| 输入 | 作用 | 备注 |
| --- | --- | --- |
| **逻辑拓扑图** | 逻辑结构：节点、单向门、锁钥门、连通链路 | 可手绘/图片/已填的结构化拓扑 |
| **范围图** ★新 | **空间范围**：边界、轮廓、大致分区 + 比例标定 | 给"相对位置"提供参照系 |
| **氛围图与叙述** | 基调、风格、机关、叙述 | 已有设计（§2.5） |
| **规则与说明** | 之前的规则、规范、拆分要求 | **可后续补充**，纳入 digest |

### 2.3 识别（辅助）

把导入的**逻辑拓扑图**与**范围图**解析成结构化数据：图上的节点/连线/单向标记/锁钥标记 → `topology`；范围图的边界与分区 → 拆解的参照系。

- **产出候选、人工确认**，绝不静默定稿。
- 边界诚实：范围图只有轮廓时，具体尺寸仍标 `estimated`。

### 2.4 拆解：触发时机与提案内容 ★

**触发时机**（你描述的流程）：

```
1. 一个模块一开始可能是空的
2. 我导入:逻辑拓扑图 + 范围图 + 其他必要说明(规则/规范,后续可补)
3. 我在 DSH 里说:"把这个逻辑拓扑图按范围图拆开,
   拆成多少个节点、哪个节点大概怎么连接、高度如何、相对位置在哪里"
4. 你在网页上帮我生成出来
```

**提案内容**（对应你点名的四件事）：

| 你的说法 | 提案里的字段 |
| --- | --- |
| 拆成多少个节点 | `nodes[]`：数量 + 每个节点的角色/规模 |
| 哪个节点大概怎么连接 | `links[]` 落到模块间：`moduleLinks[]`（保留单向/锁钥语义） |
| 高度如何 | 每节点的相对标高与层高（父级局部坐标） |
| 相对位置在哪里 | 每节点在父 Scope 局部坐标里的位置（依范围图） |

提案同时给出**基础构型**（体块 + 端口），因为精度要求就是"只到体块+端口"。

### 2.5 展示：多套模板

同一份拆解结果，多种呈现（你说的"多套模板展示也可以"）：

| 模板 | 内容 |
| --- | --- |
| **平面位置图** | 范围图作底图 + 节点框 + 相对位置 + 链路连线 |
| **拓扑语义图** | 突出逻辑语义：单向门/锁钥门/捷径着色、锁钥依赖 |
| **3D 体块预览** | 高度 + 体块，检查层高与搭接 |
| **独立展示页** | 把上述任一模板导出为**自包含网页**，可单独打开/发给他人评审 |

### 2.6 拆解确认流程（递归执行，每层走一遍）

| 轮次 | AI 提案 | 规则校准 | 人工确认 |
| --- | --- | --- | --- |
| R0 | — | **上下文完整性**：inputs 是否齐全、digest 是否最新 | 补齐缺失输入 |
| R1 | 识别结果 | 拓扑连通性、锁钥可得性、单向语义 | 修正拓扑 |
| R2 | **横向拆解**：哪些节点合成一个模块 | 每模块是否有进出口、孤立节点 | 合并/拆分/改名 |
| R3 | **纵向拆解**：哪些节点展开成子 Scope | 子层能否自洽、深度预警 | 展开/收起/定深度 |
| R4 | **模块间连接** + 高度 + 相对位置 | 模块图连通性、端口数是否匹配 | 文字或图形调整 |
| R5 | **基础构型**（体块 + 端口） | 尺寸与端口合规 | 调尺寸/出口位置 |
| R6 | 交付总检 | **`error` 必须为 0** | 确认交付 |

每轮产物都是**结构化、被确认过的数据**（带 `proposedBy: ai|human`、`confirmed`、`basedOnInputsDigest`），不是聊天记录。R2–R5 在子 Scope 里**再走一遍** —— 这就是递归的工作流。

## 3. 阶段间契约：关卡概念包 CP-1

### 3.1 文件形态（分文件，与既有约定一致）

```text
concept/
  root.concept.json                    # 根 Scope
  scopes/
    sc_amusement-park.concept.json
    sc_haunted-house.concept.json
    sc_village.concept.json
  inputs/                              # 输入上下文包引用的原始材料
    topo-01.png  extent-01.png  mood-01.png  rules-v3.md
```

每个 Scope 一文件，`parentScopeId` + `children[]` 建立嵌套，**深度不设上限**。

### 3.2 Scope 文件结构

```jsonc
{
  "spec": "blockout.concept.scope",
  "specVersion": 1,
  "id": "sc_haunted-house",
  "name": "鬼屋",
  "parentScopeId": "sc_amusement-park",
  "inputsRevision": 3,                 // 对应 inputs bundle 的 revision
  "atmosphere": { /* 可省略 → 继承 */ },
  "topology":   { /* 本层逻辑拓扑 */ },
  "content": {
    "blocks": [],
    "instances": [ { "id": "in_hall", "childScopeId": "sc_hall",
                     "transform": { "position": [0,0,0], "rotation": 0 } } ],
    "ports": [ { "id": "pt_house_in", "linkId": "lk_A", "position": [0,0], "rotation": 0, "width": 150,
                 "internalRef": { "childScopeId": "sc_hall", "portId": "pt_hall_north" } } ]
  },
  "delivery": { "status": "draft|confirmed|delivered", "confirmedAt": "…" }
}
```

### 3.3 契约硬规矩

1. **逻辑层不含世界坐标**；`graphLayout` 仅排版。
2. **每层只承诺本层精度**（体块 + 端口）。
3. **提案必须带 `basedOnInputsDigest`**；输入变更后旧提案标 `stale`。
4. **禁止自包含**（环检测）。
5. **身份带路径**：`scopePath + 本地 id`；改名/移动/重排/重新生成都不变。
6. **禁用跨层直连**；跨层必须经边界端口逐层落地。
7. **出处可查**：`proposedBy` 区分 AI/人工；不可观测值标 `estimated`。
8. **交付门递归**：本层与所有子层 `error` 均为 0 才能 `delivered`。
9. **版本与迁移**：破坏性变更必须提供迁移（沿用 `docs/rebuild/README.md` 变更规则）。

## 4. 阶段二 · 拼接与转化

### 4.1 导入与递归组装

导入概念包 → 建立 Scope 树 → 叶子生成基础构型模块、复合节点生成复合模块 → 在无限画布拼接（**这一刻才产生世界位置**）→ 3D 预览。
`assembly-resolver` 改深度优先，累乘 transform，产出**展平的部署几何**。

### 4.2 嵌套下的身份（关键改动）

```
旧: projectId / moduleInstanceId / blockId
新: projectId / scopePath… / moduleInstanceId / blockId
```

UE 标签同步升级，否则重复 Apply 会产生重叠 Actor。**接嵌套前必须先做这一步。**

### 4.3 DSH HTTP 接口（两阶段共用）

| 能力 | 接口 | 阶段 |
| --- | --- | --- |
| 读上下文 | `GET /scopes/{id}/inputs` → 全部材料 + digest | 一 |
| 写提案 | `POST /scopes/{id}/proposals` → 拆解结果（带 digest） | 一 |
| 生成展示 | `POST /render {template, scopeId}` → 页面/图片 | 一 |
| 定位 | `GET /issues/{id}/location` → `{scopePath, moduleId, blockIds, position, bounds, camera}` | 二 |
| 截图 | `POST /capture {target, camera}` → PNG | 二 |
| 修改 | `POST /commands {text\|batch}` → 校验 → 差异 → 确认 → 事务 | 一 & 二 |
| 导出 UE | dry-run → 确认 → Apply → 回读 | 二 |

工作方式与你现在的习惯一致：在 DSH 里说"我遇到什么问题"，我调这些端点读全上下文、定位、截图、改、复核。

### 4.4 回改与合并

- 阶段二保存 `conceptRef`（scope id + specVersion + 元素 id）。
- 重导入按 **scopePath + 元素 id** 增量对齐：新增/更新/保留/冲突四类列出。
- **人工在阶段二改过的模块默认不被覆盖**；要覆盖必须显式选择"以概念包为准"。
- 阶段一输入被补充（`revision` 递增）→ 受影响的下游内容标 `stale` 并列出，不静默重算。

## 5. 可行性评估

**结论：可以做，不需要新引擎。** 三点理由：

1. **组合机制已存在**：模块定义 → 实例 → 部署几何，本来就是为复用与组合设计的，改递归是加一层调用。
2. **UE 是平的**：嵌套只服务设计表达，导出展平，复杂度不渗透到 UE 侧。
3. **每层同构**：所有 Scope 结构一致，UI 与校验器**写一份递归复用**。

**主要代价与应对：**

| 代价 | 应对 |
| --- | --- |
| 身份从三段变路径 | 先做 §4.2，一次性升级 + 迁移 |
| 递归展开性能（深 × 实例多） | 展平结果缓存，只重算变更子树 |
| 导航心智负担 | 面包屑 + 下钻；每层只显示本层精度 |
| 交付门要递归聚合 | 校验器递归汇总 `error` |
| 深度失控（拆太碎） | R3 做**深度预警**，不硬性设上限 |
| 上下文漂移（看漏输入） | **`inputsDigest` 强制约定**（§2.1） |
